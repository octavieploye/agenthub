# Proposal Proof

Stress-test your proposal before you send it. Reads the proposal as a skeptical client would, identifies the objections and gaps you cannot see from the inside, and delivers a structured critique before it goes out.

## When to Use

- "I've written a proposal and want a second opinion before I send it"
- "Help me find the weak points in this proposal"
- "What objections is the client likely to raise?"
- "I want to stress-test this before it goes out"
- Invoked as Step 2 of the Before the Meeting bundle (uses price verdict from Price Proof if available)

## What You Need Before Starting

- **The full proposal text** — paste it in directly
- **Client context** (optional but valuable): who is the client, what sector, what is their procurement style?
- **Price verdict from Price Proof** (if running as part of the bundle): the confirmed rate and rationale

If the proposal is not provided, ask for it before proceeding.

## Workflow

1. **ANALYZE** — Read the proposal as the client would
   - Map each section: executive summary, scope, deliverables, timeline, pricing, value proposition
   - Identify the narrative: what problem is being solved, what outcome is promised, what evidence supports it?
   - Note the structure: is it client-centric or supplier-centric?

2. **PLAN** — Build a client-perspective critique map
   - For each section: what would a skeptical client flag?
   - Identify the 3 most critical sections (where the deal is won or lost)
   - If price verdict from Price Proof is available, cross-reference pricing section against validated rate and rationale

3. **COUNTERCHECK** — Run a structured challenge
   - Unstated assumptions: what is the proposal assuming the client already knows or agrees with?
   - Scope ambiguities: where is the scope vague enough for a client to dispute scope creep later?
   - Pricing justification gaps: where is the price stated but not defended?
   - Missing proof points: where is value asserted but not demonstrated?
   - Sections where value is described in supplier language, not client outcome language

4. **TEST** — Simulate the top 3 client objections
   - Objection 1: the most likely pushback (usually price or scope)
   - Objection 2: the second most likely (usually timeline or proof of competence)
   - Objection 3: the sleeper objection (often a procurement or process mismatch the user didn't anticipate)
   - For each: why the client will raise it, and what in the proposal triggered it

5. **ACT** — Deliver the verdict
   - Section-by-section critique (severity: CRITICAL / REVISE / MINOR)
   - Top 3 objections the client will raise + what to fix in the proposal to preempt each
   - The single highest-leverage reframe that improves acceptance probability
   - send / revise verdict

## Output

- Section-by-section critique with severity ratings
- Top 3 anticipated client objections
- Specific fixes for each gap identified
- Highest-leverage reframe
- send / revise verdict

## Constraints

- Never rewrite the proposal — critique it and specify fixes, let the user rewrite
- Never skip the COUNTERCHECK step — surface assumptions the user cannot see from inside the proposal
- If the proposal is incomplete (placeholder sections, missing pricing), flag this before proceeding
- Cross-reference price section against Price Proof output if it is available

## Common Mistakes

| Mistake | Fix |
|---|---|
| Only checking surface quality (clarity, grammar) | Go deeper — check commercial assumptions, scope ambiguity, and proof gaps |
| Missing the sleeper objection | Always generate a third objection that is non-obvious |
| Rewarding client-centric language that isn't actually there | Read literally — if the value is asserted but not shown, flag it |
| Ignoring pricing section when Price Proof output is available | Always cross-reference if bundle context is present |
